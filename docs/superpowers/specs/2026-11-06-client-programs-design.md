# Client training programs — approved direction

User accepted the recommendation on 2026-11-06 following the independent client-page review. This is the first delivery: training programs and client UI/UX; nutrition is a separate subsequent delivery beginning with energy/macronutrient goals and habits. Preserve Clinical Field Notes, Vietnamese type, all themes, existing clinical/reference workflows, and source-specific evidence limits.

## Outcome
A PT can open the client's overview, create a weekly program manually or request an AI draft, edit goals, schedule, exercises and training methods, save a revision, deliberately activate it, record an actual workout with individual sets, and compare completed work with its prescription. Switching detail sections preserves unsaved work and consultation context in the current client workspace. No automatic medical clearance or autonomous plan activation.

## Program contract
Program input includes title, goal enum (strength/hypertrophy/fat_loss/general_fitness), specific goal and review date, weeks, minutes per session, available equipment/constraints, rationale and progression notes, and 1–7 scheduled sessions with unique weekdays. Each session has stable ID, name, and 1–12 exercise prescriptions. Prescriptions have stable ID, optional existing Atlas exercise ID, explicit exercise/variant name, sets, rep range, target load/unit, rest seconds, optional set RIR, tempo, method (straight sets or superset with explicit group), and notes. PT-authored custom names are allowed and identified as having no attached Atlas evidence. AI may only select known catalog IDs and must not invent variant identity or numerical evidence.

Saves produce immutable revisions with server identity/time and draft/active/archived status; at most one active revision per client, switched atomically. Old active revisions are archived, never deleted automatically. Saved and unsaved states are distinct. Errors and absent migrations do not silently fall back to another data store. Missing records, malformed payloads, partial configuration, cross-client references and concurrent activation are handled explicitly.

## Workouts and feedback
A workout snapshots the prescription and links to its plan revision/session, with performed date, individual set reps/load/unit/completion, optional session RPE and notes, and in-progress/completed state. Saving uses a stable workout ID for retry/idempotence; cross-client links are rejected. Completed requires every prescribed set accounted for; no default completion. History shows planned versus actual and permits reopening an existing record without duplicating it. Existing standalone training log and Atlas deep links remain available. Chat receives a bounded recent training summary as well as existing profile/biomarker context.

## AI and evidence
AI generation is explicit and does not persist/activate anything. It receives structured intake, existing relevant profile data, bounded recent training history, and existing curated training evidence with actual sources/dates/access scopes. Output is validated before becoming an editable draft. Invalid output or upstream failure preserves the existing draft, gives a retryable message, and never masquerades as a successful program. Source context means material supplied to the model, not verified entailment or independent clinical review; reviewer remains null. No new automatic dose rules or clinical claims are introduced. The normal manual path works without AI configuration.

## Interface
Default route becomes Overview. Main work destinations are Overview, Program, Workout/History and clinical Profile group, with consultation explicitly available. Existing query URLs remain compatible. Overview shows the client's goal, active program/empty state, upcoming scheduled session, and clear next action. The program uses a compact intake followed by a readable weekly/session editor and revision list. Workout entry follows the prescribed exercise order and shows previous comparable results. Clinical tools use a secondary grouped navigation; urgent symptom guidance remains visible while repeated generic caution text is reduced. No decorative eyebrow, icon-as-label, or new palette.

Keep editing sections mounted once visited, scoped to the client, so switching sections does not discard form/chat state. Do not persist medical drafts into long-lived browser storage. Show clear unsaved status on program/workout editors and preserve drafts on failed requests; an explicit discard/reset is deliberate. Refresh/navigation outside the current client is outside in-memory draft persistence; communicate this limit beside drafts.

## Validation and delivery
Use TDD for model, persistence, generation and draft-loss behavior. Tests operate on temporary synthetic stores/mocked services; never write real client data or send live AI requests. Verify TypeScript/lint, meaningful existing client/chat/log regressions, React Doctor, full design source detector, and affected rendered routes on desktop/mobile. Inspect screenshots and keyboard/focus behavior with CUA. Record unrun/remaining findings without claiming accessibility or medical certification. For Supabase include migration and executable instructions; do not apply a remote migration without authorization. Integrate the verified branch back into the user's source workspace while preserving the review artifact and other work.
